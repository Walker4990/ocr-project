# 개요

DocuLens는 소상공인이 주고받는 거래명세서(이미지/PDF)를 OCR로 읽어 구조화 데이터(헤더 + 품목 표)로 변환하고,
사람이 검수·수정한 뒤 엑셀/CSV로 내보내는 웹 서비스다.
숨고(재능 마켓)에서 "서류 입력 자동화" 의뢰를 받기 위한 **포트폴리오 프로젝트**이며,
단순 OCR 데모가 아니라 실무 워크플로 전체(업로드 → 추출 → 검증 → 검수 → 내보내기)와
비용/보안/운영 요소를 보여주는 것이 목적이다.

## 타깃 사용자 (의뢰인 페르소나)
- 거래명세서를 수기로 엑셀에 옮기는 소상공인, 소규모 유통/제조 사업자, 회계 담당자
- GPU 서버가 없고, 월 수천~수만 원대 VPS 또는 일반 PC 환경에서 운영해야 한다

## 핵심 가치
1. CPU만으로 동작한다 (GPU는 선택 옵션)
2. 추출 결과를 그대로 믿지 않고 검증한다 (합계/체크섬/수량×단가)
3. 사람이 쉽게 고칠 수 있다 (원본 이미지 위 bbox 오버레이 검수 UI)
4. LLM은 옵트인이다 (끄면 완전 오프라인, 켜도 이미지가 아닌 OCR 텍스트만 전송)

## 비목표 (이번 범위 밖)
- 사업자등록증, 세금계산서(전자), 영수증, 신분증 등 다른 문서 유형 (확장 과제로만 기록)
- 다중 사용자 권한/결제/조직 관리
- 모바일 네이티브 앱
- 실제 거래처 정보가 담긴 문서 사용 (모든 샘플은 합성 데이터)

# 기술 아키텍처

## 스택
- 프론트엔드: Next.js 15 (App Router), React 19, TypeScript, Tailwind CSS, shadcn/ui, Zustand, React Hook Form + Zod
- 백엔드: FastAPI (Python 3.12, uv로 버전 고정), Pydantic v2, SQLAlchemy 2 + Alembic
- 큐/워커: Redis + arq (비동기 OCR 잡)
- DB: PostgreSQL, 파일 스토리지는 로컬 디스크(S3 호환으로 교체 가능한 인터페이스)
- OCR: PaddleOCR 3.x (PP-OCRv5 한국어, 기본), PP-StructureV3 계열 표 구조 인식
- 전처리: OpenCV, PDF 분리(pypdfium2 또는 PyMuPDF 중 라이선스 검토 후 선택)
- 선택 엔진: PaddleOCR-VL (GPU 있을 때만), Tesseract (비교용 베이스라인)
- LLM(선택): Anthropic Claude API, 기본 모델은 Haiku 급, 설정으로 교체 가능
- 인프라: Docker Compose (api, worker, web, postgres, redis), GitHub Actions CI
- 테스트: pytest, Vitest, Playwright (E2E)

## 저장소 구조
```
apps/web        Next.js 프론트엔드
apps/api        FastAPI 백엔드
  app/controllers   라우터 (HTTP 입출력만)
  app/services      비즈니스 로직
  app/repositories  DB 접근
  app/ocr           OcrEngine 구현체, 전처리
  app/extraction    Extractor 구현체, 파서
  app/validation    검증기
  app/workers       arq 작업
samples         합성 거래명세서와 정답 라벨 (골든셋)
benchmarks      벤치마크 스크립트와 결과
docs            아키텍처 다이어그램, 케이스 스터디
```

## 설계 원칙 (프로젝트 규칙)
- 백엔드는 Controller → Service → Repository 레이어를 지키고 의존성은 주입한다
- 레이어를 건너뛰지 않는다 (Controller에서 Repository 직접 호출 금지)
- `any` 금지(TS), 타입 힌트 필수(Python, mypy 또는 pyright 통과)
- 에러를 삼키지 않는다. 도메인 예외를 정의하고 핸들러에서 일관된 에러 응답으로 변환한다
- 모든 요청에 `requestId`를 부여하고 로그와 에러 응답, 워커 잡까지 전파한다
- 과도한 추상화 금지. 추상화는 OcrEngine, Extractor, StorageBackend 세 곳으로 제한한다
- TDD: 실패하는 테스트를 먼저 작성한 뒤 구현한다
- 새 라이브러리 도입은 사전 제안 후 확인을 받는다
- 프론트/백엔드 타입은 OpenAPI에서 생성해 동기화한다 (openapi-typescript)

## 데이터 모델 (요약)
- Document: id, 원본 파일 경로, 해시, 상태(uploaded/processing/extracted/reviewed/failed), 페이지 수, 생성/수정 시각
- OcrResult: document_id, 엔진명, 처리시간(ms), 토큰 목록(텍스트, bbox, 신뢰도)
- Extraction: document_id, 추출 방식(rule/llm), 헤더 필드 JSON, 신뢰도, 검증 결과, 리뷰 상태
- LineItem: extraction_id, 순번, 품명, 규격, 수량, 단가, 공급가액, 세액, 비고, bbox
- ReviewEdit: 필드 변경 이력 (누가/언제/이전 값/이후 값)

## 추출 대상 필드 (거래명세서)
- 헤더: 발행일, 문서번호, 공급자(상호, 사업자등록번호, 대표자, 주소), 공급받는자(상호, 사업자등록번호)
- 품목: 품명, 규격, 수량, 단가, 공급가액, 세액, 비고
- 합계: 공급가액 합계, 세액 합계, 총 합계금액

## 검증 규칙
- 사업자등록번호 10자리 체크섬 (가중치 1,3,7,1,3,7,1,3,5 알고리즘)
- 각 품목: 수량 × 단가 = 공급가액 (허용 오차 설정 가능)
- 품목 공급가액 합계 = 헤더 공급가액 합계
- 공급가액 합계 + 세액 합계 = 총 합계금액
- 날짜 형식 정규화 (YYYY-MM-DD), 금액 정규화 (콤마, 원 단위 제거)
- 검증 결과는 필드 단위 경고로 저장하고 UI에 표시한다
- 검증기는 추출 방식(rule/llm)과 무관하게 동일하게 적용한다

## 추출 전략 (옵트인 하이브리드)
1. OCR 토큰과 표 구조를 입력으로 받는다
2. 규칙 추출기: 헤더 키워드 기반 필드 추출, 품목 표는 열 헤더 매핑으로 파싱
3. 신뢰도가 낮거나 필수 필드가 비면 LLM 추출기를 호출한다 (설정에서 켠 경우에만)
4. LLM 입력은 OCR 텍스트와 좌표 요약만 사용한다. 이미지는 전송하지 않는다
5. LLM 출력은 Pydantic 스키마로 강제하고, 파싱 실패 시 규칙 결과로 폴백한다
6. 호출 상한(일/월), 파일 해시 기반 결과 캐시, 타임아웃, 재시도(백오프)를 둔다
7. API 키가 없으면 LLM 기능은 자동 비활성화되고 UI에서도 숨긴다
8. 라이브 데모에서는 샘플 문서에만 LLM을 허용한다

## OCR 엔진 계약
- `OcrEngine` Protocol: `recognize(image) -> OcrPage` (토큰: text, bbox, confidence), `name`, `supports_gpu`
- 엔진은 설정(환경변수)으로 선택한다. GPU 엔진은 사용 가능할 때만 등록된다
- 엔진별 처리시간을 기록해 벤치마크에 사용한다

## API 개요
- POST /api/documents (업로드, 파일 형식/크기 검증) → 202 + document_id
- GET /api/documents, GET /api/documents/{id}
- GET /api/documents/{id}/events (SSE, 처리 진행률)
- GET /api/documents/{id}/extraction
- PATCH /api/documents/{id}/extraction (검수 수정)
- POST /api/documents/{id}/approve, POST /api/documents/{id}/reject
- POST /api/documents/{id}/reextract?mode=rule|llm
- GET /api/documents/{id}/export?format=xlsx|csv
- GET /health
- 모든 응답과 에러 본문에 requestId를 포함한다

## 보안/개인정보
- 업로드 허용 형식(png, jpg, pdf)과 최대 크기 제한, 매직 바이트 검사
- 업로드 파일 보관 기간 정책 (기본 N일 후 자동 삭제, 설정 가능)
- 레이트 리밋, CORS 화이트리스트
- 시크릿은 환경변수로만 주입하고 저장소에 커밋하지 않는다 (.env.example 제공)
- 로그에 문서 본문/개인정보를 남기지 않는다

## 샘플 데이터 (골든셋)
- 실제 거래 문서는 사용하지 않는다
- 서로 다른 양식 템플릿 5종 이상에 가짜 데이터를 채워 렌더링해 30장 이상 생성한다
- 생성 시 정답 라벨(JSON)을 자동으로 함께 만든다
- 난이도 변형: 깨끗한 스캔, 기울어짐, 저해상도, 스마트폰 촬영 느낌(원근/그림자/노이즈)

# 개발 단계

## P1. 기반 (약 3~4일)
- 모노레포 구조, uv(Python 3.12) 및 npm 워크스페이스 구성
- Docker Compose (postgres, redis, api, worker, web)
- FastAPI 골격: requestId 미들웨어, 도메인 예외와 에러 핸들러, 구조화 로깅, /health
- Next.js 골격: 레이아웃, shadcn/ui 설정, API 클라이언트
- GitHub Actions CI: 백엔드 테스트/린트/타입, 프론트 test/tsc/lint
- 합성 골든셋 생성기 작성과 30장 이상 생성
- 완료 기준: docker compose up으로 전체 스택 기동, CI 통과

## P2. OCR 코어 (약 5~6일)
- OcrEngine Protocol과 PP-OCRv5 한국어 어댑터 (TDD)
- 전처리: 기울기 보정, 대비 개선, 리사이즈, PDF 페이지 분리
- 표 구조 인식 통합과 품목 표 셀 추출
- Tesseract 베이스라인 어댑터
- PaddleOCR-VL 어댑터 (GPU 있을 때만 활성화)
- 벤치마크 스크립트: CER, 필드 정확도, 표 셀 정확도, 처리시간을 골든셋 변형별로 측정해 마크다운 표로 출력
- 완료 기준: 벤치마크 표 생성, CPU에서 1페이지 처리시간 측정값 기록

## P3. 추출·검증·API (약 4~5일)
- 규칙 추출기(헤더)와 품목 표 파서
- 검증기 전체 (체크섬, 수량×단가, 합계 대조, 정규화)
- DB 스키마, 마이그레이션, Repository/Service/Controller
- 업로드 → arq 큐 → 워커(전처리 → OCR → 추출 → 검증 → 저장) 파이프라인과 SSE 진행률
- LLM 추출기(옵트인): 스키마 강제 출력, 캐시, 호출 상한, 폴백
- 완료 기준: API만으로 업로드부터 검증 결과 JSON까지 E2E 통과, 규칙 vs 규칙+LLM 벤치마크 비교

## P4. 검수 UI (약 5~6일)
- 문서 목록(상태 필터, 검색)과 업로드 화면(드래그앤드롭, 진행률 SSE)
- 검수 화면: 원본 이미지 위 bbox 오버레이, 필드 클릭 시 해당 영역 포커스, 신뢰도 색상 표시
- 수정 폼(React Hook Form + Zod), 검증 경고 인라인 표시, 품목 행 추가/삭제/수정
- 승인/반려, 재추출(rule/llm) 버튼, 수정 이력
- 엑셀(xlsx)/CSV 내보내기
- 완료 기준: Playwright E2E로 업로드 → 수정 → 승인 → 내보내기 통과

## P5. 마감과 포트폴리오화 (약 3~4일)
- 라이브 데모 배포(CPU), 샘플 문서 원클릭 체험, LLM은 샘플에만 허용
- 보안 항목 적용 (레이트 리밋, 파일 삭제 정책, 형식/크기 제한)
- README: 아키텍처 다이어그램, 벤치마크 표(CPU 기본 vs GPU 옵션 vs 규칙+LLM), 데모 GIF, 실행 방법
- 숨고 프로필용 케이스 스터디: 문제, 접근, 정확도 수치, 처리시간, 비용, 확장 가능 영역

- 사진 촬영 문서 정확도 하락 → 전처리 강화, 신뢰도 임계값, 검수 UI, 한계를 README에 명시

- 범위 확장 → 문서 유형은 거래명세서 하나로 끝내고 나머지는 확장 과제로 기록
